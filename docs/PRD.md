# Product Requirements Document

**Status:** Planning queue resolved (26 decisions accepted, 2026-04-28). One decision (005, backend framework) flagged as open for re-evaluation before serious build starts.

## How to read this doc

Each section below corresponds to a decision area. When a decision is made, this PRD records the *outcome* (what we're building), and the corresponding `decisions/NNN-*.md` file records the *reasoning* (why we chose it, what we considered, what assumptions we're making).

Sections marked **[PENDING]** have not been resolved yet.

## v1 implementation scope

The architecture documented here describes the **full Plaud Automation Layer service** — a multi-consumer headless backend that ingests transcripts, runs them through pipelines and agents, captures verdicts, learns over time, and delivers outputs to consuming apps via signed webhooks.

**v1 ships the Plaud-via-email-forward → CRM-output slice end-to-end as a single coherent feature.** Other transcript sources (Plaud API direct per [013](decisions/013-transcript-source-adapter.md), marketing-app interaction capture, future direct API uploads) are deferred but the architecture supports them by construction.

The v1 build proves the architecture by shipping one north-star pipeline (specific pipeline TBD per [001](decisions/001-target-user-and-v1-scope.md)) on real Plaud transcripts forwarded to a Plaud-account-controlled email address that this service owns ([012](decisions/012-email-vendor.md)). 4tradesCRM is the v1 consuming app; marketing app integration follows once the Plaud slice is stable.

## Reconciliation with 4tradesCRM-side Plaud feature spec

There is (or was) a Plaud feature spec in the 4tradesCRM repo written under the assumption that Plaud integration would be implemented inside the CRM (with paths like `backend/src/email-watchers/`, direct `Lead`/`Task` writes, `settings.features.plaudIntegration`, etc.). That spec describes a *CRM-internal feature*; this PRD describes a *shared automation service consumed by the CRM*.

**Translation table for reading the CRM-side Plaud feature spec against this architecture:**

| CRM-side Plaud spec says | Service architecture interpretation |
|---|---|
| `backend/src/email-watchers/` | Voice-app's Resend inbound parse webhook + ingestion adapter ([012](decisions/012-email-vendor.md), [013](decisions/013-transcript-source-adapter.md)) |
| `backend/src/plaud/` | Voice-app's Plaud source adapter under `apps/voice-app/src/integrations/plaud/` (or wherever the framework re-eval per [005](decisions/005-backend-framework.md) lands it) |
| `frontend/components/PlaudReviewQueue.tsx` | Review UI lives in CRM (per [003](decisions/003-primary-user-surface.md) — consuming-app-canonical review). CRM renders proposed outputs received via webhook from voice-app. |
| Direct `Interaction`/`Lead`/`Task` writes | Voice-app emits proposed outputs via outbound webhook; CRM's webhook receiver creates `Interaction`/`Lead`/`Task` records in its own DB ([020](decisions/020-integration-contracts.md)) |
| `settings.features.plaudIntegration` | Voice-app-owned tenant config in `tenant_destinations` ([020](decisions/020-integration-contracts.md)); may mirror or sync from a CRM-side feature toggle |
| Existing CRM user/inbox identity | Voice-app receives or resolves `tenantId`, `actorUserId`, `mailboxId` from CRM-issued JWTs ([010](decisions/010-auth-provider.md)) and from the per-tenant Plaud-forwarded inbound address |

**Action item (tracked outside this PRD):** the CRM-side Plaud feature spec should be amended (or replaced) with a "Plaud integration in CRM" doc that describes only the CRM's contribution: receiving voice-app webhooks, rendering the review queue, sending verdict events back, displaying delivered artifacts. CRM-internal email-watching is no longer needed because Plaud forwards directly to voice-app's inbound address.

## 1. Product framing
- **Target user & v1 scope** ([001](decisions/001-target-user-and-v1-scope.md)): v1 serves the author only. "Done" = a single north-star-class pipeline (specific pipeline TBD) runs end-to-end on real Plaud transcripts via email, durably. Multi-tenancy is structurally present in code and data model but only one tenant exists in production. Pipeline routing is trivial in v1. Onboarding, billing, self-serve, and admin tooling are out of scope for v1. Specific north-star pipeline choice deferred to a later sub-decision.
- **Primary user surface** ([003](decisions/003-primary-user-surface.md), substantively amended 2026-04-28): voice-app is a backend service with **zero user-facing UI in v1**. Outputs flow to consuming apps (4tradesCRM, marketing app, future third-party CRMs) via outbound webhooks per [020](decisions/020-integration-contracts.md); consuming apps render review/edit/accept/reject affordances in their own UI; verdicts return to voice-app via inbound webhooks. Super-admin views live in a separate Next.js app per [019](decisions/019-repo-structure.md). The `review_required` flag on `outputs[].kind` (per [015](decisions/015-pipeline-definition-format.md)) is preserved — it tells voice-app whether to hold an output until verdict arrives or deliver immediately. The *location* of review is the consuming app.

## 2. Architecture foundations
- **Language / runtime** ([004](decisions/004-language-and-runtime.md)): TypeScript on Node.js, end-to-end (backend, frontend, pipeline definitions). Strict TS (`strict`, `noUncheckedIndexedAccess`) + zod for runtime boundary validation. Shared types via a `@platform/shared` package.
- **Backend framework** ([005](decisions/005-backend-framework.md)): Next.js with App Router (currently). **Flagged 2026-04-28 as open for re-evaluation** before serious build starts — the original choice assumed voice-app had a dashboard, which the [003](decisions/003-primary-user-surface.md) reframe removed. NestJS or Hono may be more idiomatic for a pure backend service. Resolution: hello-world the Plaud-ingestion-to-CRM-output flow in each candidate (~1 day) and pick the cleanest. super-admin stays Next.js regardless.
- **Repo structure** ([019](decisions/019-repo-structure.md)): Monorepo with two Next.js apps + shared packages. `apps/voice-app/` (the backend service — API routes, Inngest functions, webhook receivers, no React UI), `apps/super-admin/` (separate Next.js app with React UI for ops/super-admin views, reads voice-app's admin APIs), `packages/shared/` (types, Zod schemas, audit-log shapes, webhook contracts, event-name constants), `packages/auth/` (`jose`-based JWT verifier shared by both apps). pnpm + Turborepo workspace tooling. Two Vercel projects deploy from the same repo. ESLint enforces module boundaries — apps consume each other only via API, never via direct imports.
- **Hosting / deployment** ([011](decisions/011-hosting-and-deployment.md)): Vercel. Production from `main`; preview deploys per PR. Custom domain `voice.4trades.io` (CNAME to Vercel). Vercel region matches Supabase region. Environment variables segmented by environment in Vercel UI. 4tradesCRM is also on Vercel — single-vendor consolidation across both products.

## 3. Data layer
- **Primary database** ([007](decisions/007-primary-database-and-vector-store.md)): Supabase (managed Postgres). All non-Inngest durable state lives here: users/tenants, transcripts, pipeline-run metadata, outputs, verdicts, retrieval corpus, native-target delivery records. `tenant_id` is a first-class column on every multi-tenant table.
- **Vector store** ([007](decisions/007-primary-database-and-vector-store.md)): pgvector inside the same Supabase Postgres instance, HNSW index. All retrieval calls flow through a `RetrievalStore` interface — no SQL with raw vector ops sprinkled through the codebase. Migration trigger to a dedicated vector DB documented: corpus >10M vectors AND p95 retrieval-latency SLO breach. Realistic trigger timing is v3 (~1,000 users), not v1 or v2.
- **Multi-tenancy model** ([008](decisions/008-multi-tenancy-model.md)): Postgres Row-Level Security with `tenant_id` columns on every multi-tenant table. User-facing queries use the anon-key client (RLS active). Service-role queries (Inngest pipelines, cron, automation) go through `withTenant(tenantId, fn)` helper utilities — no raw service-role queries in business code. **Super-admin is a v1 product concept**, mirroring 4tradesCRM's existing pattern: an `is_internal_staff` flag on user records sets an `isInternalStaff: true` JWT claim. RLS policies on multi-tenant tables include an OR clause: `(auth.jwt() ->> 'isInternalStaff')::boolean = true`. An impersonation endpoint mirrors the CRM's `/auth/impersonate/{tenantId}` — internal staff can mint a tenant-scoped JWT for any tenant. A `super_admin_audit` table records every cross-tenant access (the CRM does not have this; voice-app adds it because of more sensitive data). The dashboard exposes "super admin mode" views only when the JWT carries the flag. CI test suite includes a multi-tenant RLS isolation test from v1.

## 4. Workflow & pipelines
- **Workflow / job engine** ([006](decisions/006-workflow-engine.md)): Inngest (hosted free tier in v1; self-host is the documented escape hatch). Pipelines are Inngest functions invoked by events; each step is a `step.run` call (checkpointed, auto-retried). Human-in-the-loop pauses use `step.waitForEvent` matched on run ID. Inngest owns durable run state; our database does not duplicate step state. Inngest's run-inspector is the v1 pipeline-debugging surface.
- **Pipeline definition format** ([015](decisions/015-pipeline-definition-format.md)): TypeScript code in `pipelines/` directory. Each pipeline file exports a default `definePipeline({...})` call wrapping an Inngest function with structured metadata (id, triggers, requiresCRMIntegration, outputs[]). Domain step helpers (`step.review`, `step.callCRM`, future `step.invokeAgent`) wrap Inngest primitives with our review/CRM/agent semantics. Metadata validated via Zod at module load time. Auto-discovered pipeline registry exposes pipelines to Inngest, the dashboard, and the routing layer. Engineer-authored in v1; non-engineer authoring deferred to v3+.
- **Agent and tool architecture** ([016](decisions/016-agent-and-tool-architecture.md)): Three-layer architecture — pipelines orchestrate (deterministic), agents do LLM-driven sub-tasks, tools are deterministic typed functions called by both. Agents defined via `defineAgent({...})` in `agents/<id>.ts`; tools via `defineTool({...})` in `tools/<id>.ts`. Tools are tenant-scoped by construction (`withTenant(...)` wrapper) and audit-logged. Pipelines invoke agents via `step.invokeAgent(agentId, { input })` — a durable Inngest step wrapping Vercel AI SDK's `generateText` + tool-calling. Hard execution limits per agent (`maxIterations: 8`, `timeoutMs: 5min`, `costCapUsd: $0.50` defaults; tunable). Structured `AgentLimitExceeded` errors when caps hit. Auto-discovered `agents/` and `tools/` registries. `agent_runs` and `tool_calls` audit tables. Cross-product tool sharing with 4tradesCRM deferred to v2; SKILL.md export deferred to v2.
- **Pipeline dispatch** ([017](decisions/017-pipeline-dispatch.md)): Dispatcher-based architecture. A central `routeToPipeline(transcript)` in `lib/pipelines/router.ts` decides which pipeline gets each transcript; the `pipelines/dispatcher.ts` Inngest function listens to `transcript.ingested` and emits `pipeline.${pipelineId}.requested`. Pipelines listen to their pipeline-specific event, not `transcript.ingested` directly. Every dispatch is audit-logged with a structured `reason`. **Expected evolution path documented**: v1 trivial classifier → v1.x/v2 rules + embedding-similarity fast-path → v2/v3 LLM classifier as fallback (rules/embeddings stay as fast-path) → v3+ multi-pipeline fan-out (`DispatchPlan` shape) → v4+ agent-as-dispatcher (dispatcher itself becomes an agent per [016](decisions/016-agent-and-tool-architecture.md)). LLM-based dispatch is the explicit expected endstate; the architecture is chosen to enable it without restructuring pipelines. Pipeline contracts never change across stages.

## 5. Ingestion
- **Email vendor (inbound + outbound)** ([012](decisions/012-email-vendor.md)): Resend. Inbound parse webhook receives forwarded Plaud emails at per-tenant addresses (`<tenant-id>@inbound.voice.4trades.io`); webhook validates signature, extracts attachments, emits Inngest `transcript.received` event scoped to tenant. Outbound transactional sent via Resend; React Email templates in `emails/`. `EmailService` abstraction wraps Resend so vendor swap is bounded. Verified sending domain with DKIM/SPF/DMARC. Migration trigger to Postmark if 30-day spam-folder rate >2%.
- **Transcript source adapter interface** ([013](decisions/013-transcript-source-adapter.md)): Thin source-specific Inngest handlers (one per source) parse source-specific input, resolve tenant, and emit `transcript.normalized` events. A single shared `dedupe-and-persist-transcript` Inngest function enforces `(source, external_id)` uniqueness, persists to `transcripts` table, and emits `transcript.ingested` for the routing layer. Adding a new source = one new event handler. **V1 ingests text only** (Plaud transcribes on-device; emails forward transcript text). Audio ingestion is intentionally out of scope; future-extension pattern documented (audio source emits `audio.received` → new `transcribe-audio` step → existing pipeline downstream).

## 6. Intelligence
- **Learning model & feedback architecture** ([002](decisions/002-learning-model-and-feedback-architecture.md)): v1 captures structured feedback for every pipeline run (accept / reject / edit / delta). Verdicts are first-class entities in the data model; pipeline runs have post-completion human-in-the-loop state. At pipeline-run time, the LLM prompt includes retrieved relevant past runs and their verdicts (in-context learning). Fine-tuning is deferred to v2, gated on corpus volume + eval harness + demonstrated need. LLM provider choice is not constrained by this decision.
- **LLM provider strategy** ([014](decisions/014-llm-provider-strategy.md)): Vercel AI SDK as the abstraction (`ai` + `@ai-sdk/openai` + `@ai-sdk/anthropic`). OpenAI primary, Anthropic fallback. Error-based fallback in v1 (429/503/transient 5xx → retry on Anthropic). Cost-based fallback deferred until real bill data. All LLM calls flow through `lib/llm/client.ts` — no direct provider SDK imports in pipeline code. Per-pipeline-step model tier selection (cheap-and-fast for routing; high-quality for drafting). Token usage logged per call.
- [PENDING] Prompt / context management approach
- **Memory / retrieval strategy** ([018](decisions/018-memory-and-retrieval-strategy.md)): Single `memory_items` table with `kind` discriminator (transcript / verdict / output / pipeline_run_summary). Whole-item embeddings via OpenAI `text-embedding-3-small` (1536 dims). HNSW pgvector index, GIN on metadata, composite (tenant, kind, created_at) index. RLS enforces tenant isolation. `RetrievalStore.search` extended with filters (kind, contact, recency window) and optional recency-weighted rerank (30-day half-life default). Memory enters LLM context via an explicit `recallMemory` tool — no invisible prepending. Citation-anchored output: every result has an `id` referenced in draft artifacts via `lib/memory/cite.ts` helpers. Whole-item embeddings in v1 (voice memos are short); chunking deferred until long-form content appears.

## 6.5 Integration contracts (consuming-app webhooks)
- **Integration contracts** ([020](decisions/020-integration-contracts.md)): Voice-app delivers proposed outputs to consuming apps via outbound `pipeline.output.proposed` webhooks; consuming apps return verdicts via inbound `verdict.captured` webhooks. Per-output-kind artifact schemas (Zod) in `packages/shared/contracts/output-kinds/`. Tenant configures destinations per output-kind pattern (exact match or wildcard like `crm.*`) in a `tenant_destinations` table; multiple destinations per kind are supported (fan-out). HMAC-SHA256 signing both directions, per-destination secret. Outbound delivery wrapped in Inngest `step.fetch` with retry + dead-letter to a `webhook_dead_letters` table; super-admin UI surfaces dead-letters with manual replay. Inbound responds 200 fast (signature verify + Inngest enqueue); idempotency via `eventId`.
- **Project entity model & identification** ([021](decisions/021-project-entity-model.md)): Projects are not canonically owned by voice-app — they're synced from consuming apps (4tradesCRM owns project records for fence-company-style customers; marketing app may sync independently). Voice-app stores synced project references with embeddings. An `identifyProject` Inngest step inserted between `transcript.normalized` and dedup persists `projectId` (or `null`) onto the transcript before pipeline dispatch. **v1 algorithm**: embedding fast-path (top score >0.78 AND >0.10 above runner-up) + LLM fallback for ambiguous cases. Pipelines and outputs carry `projectId`. Low-confidence cases route to a "needs project assignment" output kind that consuming apps render with a manual-attach affordance. `recallMemory` tool (per [018](decisions/018-memory-and-retrieval-strategy.md)) gains `projectId` filter for project-scoped recall.

## 7. Auth & identity
- **CRM integration shape & federation** ([009](decisions/009-crm-integration-shape.md)): Loose federation. Voice-app deployed at its own subdomain (e.g., `voice.4trades.io`); 4tradesCRM migrates JWT signing from HS256 to RS256 and exposes a JWKS endpoint; CRM has a "Voice Assistant" entry point that does a short-lived one-time-code SSO handshake with voice-app (no token-in-URL — exchanged server-to-server). Voice-app verifies CRM-issued JWTs via JWKS. Standalone customers sign up directly at voice-app's domain; voice-app mints its own JWTs in same shape (different `iss`). Voice-app pipelines write CRM artifacts (Leads, Contacts, follow-up tasks) via 4tradesCRM REST API. Pipeline definitions declare CRM-integration requirements per pipeline so a "Lead-write required" pipeline is unavailable in standalone mode rather than failing at runtime. **4tradesCRM-side work is tracked separately**: HS256→RS256 migration, JWKS endpoint, "Voice Assistant" entry point with one-time-code flow, REST API audit for required write endpoints.
- **Auth verifier (v1)** ([010](decisions/010-auth-provider.md), amended 2026-04-28): three distinct authentication paths in v1: **(a) End-user JWT** via `jose` + JWKS — 4tradesCRM-issued tokens for super-admin users accessing voice-app's admin APIs; `TRUSTED_ISSUERS` config extends to additional CRMs in v2. **(b) Service-to-service API keys** — consuming-app backends (CRM, marketing app) calling voice-app's APIs use per-app API keys stored in a `service_api_keys` table (bcrypt'd, scoped, revocable); issued/rotated via super-admin UI. **(c) HMAC-SHA256 signed webhooks** per [020](decisions/020-integration-contracts.md) — bidirectional message authentication for outbound and inbound webhooks; per-destination signing secret. Auth middleware returns a discriminated-union `AuthContext` (`'user' | 'service'`); webhook routes handle HMAC separately. No standalone end-user sign-up flow in v1.
- [PENDING] When to wire in auth (v1 vs. later)

## 8. Operations
- **Observability stack** ([022](decisions/022-observability-stack.md)): OpenTelemetry as the instrumentation layer (`instrumentation.ts` in each Next.js app; auto-instrumentation for HTTP, fetch, Postgres, Vercel AI SDK, Inngest context propagation) + Sentry as the v1 backend for errors and traces (free tier ingests OTel). Vercel Analytics for request metrics. Vercel native logs in v1. Inngest run inspector for pipeline observability. `packages/observability/` shared helpers propagate `tenantId` and `pipelineRunId` into spans. Super-admin UI surfaces domain-specific audit tables (`agent_runs`, `tool_calls`, `routing_audit`, `super_admin_audit`, `project_identification_runs`, `webhook_dead_letters`). Migration triggers documented for Honeycomb/Grafana (traces) and Axiom (logs) at v2+ scale.
- **Secrets management** ([023](decisions/023-secrets-management.md)): Vercel environment variables, segmented by environment (production/preview/dev). Both `apps/voice-app` and `apps/super-admin` configure their own scoped env vars. `.env.example` files list required keys; `vercel env pull .env.local` for local dev. Per-tenant runtime secrets (HMAC signing per destination per [020](decisions/020-integration-contracts.md)) stored in `tenant_destinations` table, encrypted with a master encryption key from Vercel env (envelope encryption). Migration trigger to Doppler documented.
- **CI/CD** ([024](decisions/024-cicd.md)): GitHub Actions, Turborepo-orchestrated. Pipeline per PR: install (pnpm cache) → lint → type-check → unit tests → RLS isolation test suite → webhook-contract validation → build (per-package Turborepo cache via Vercel free tier). On `main`: Sentry source-map upload, then Vercel's GitHub integration auto-deploys. Branch protection on `main` requires all CI checks pass, no force-push, no direct pushes. CI secrets (`SUPABASE_TEST_DB_URL`, `SENTRY_AUTH_TOKEN`, `VERCEL_TOKEN`) in GitHub Actions secrets, not Vercel.

## 9. Productization
- **Billing — when and how** ([025](decisions/025-billing.md)): No voice-app-level billing in v1 (author-only). v2 bills through consuming apps' existing subscription models — customers pay 4tradesCRM or marketing app on existing terms; voice-app's costs are part of consuming product's COGS. Voice-app exposes per-tenant usage metrics via admin APIs (LLM tokens, agent runs, transcripts processed, webhook deliveries) so consuming apps can surface usage and apply usage-based pricing. v3+ standalone billing (Stripe) deferred to a future decision if/when standalone customer materializes.
- **Admin / support tooling**: Provided by `apps/super-admin/` per [019](decisions/019-repo-structure.md), reading voice-app's admin APIs. Surfaces audit tables, dead-letter replay, super-admin impersonation per [008](decisions/008-multi-tenancy-model.md), per-tenant usage views.
- **Compliance posture** ([026](decisions/026-compliance-posture.md)): "Good security defaults from day one; framework certification deferred until a customer asks." **Tiered retention by data type**: raw transcripts and pipeline outputs purged at 90 days (standard B2B); verdicts retained 1 year (structured learning signal); pipeline-run summaries indefinite (PII-minimized at write-time, enforced by lint rule); audit logs 1+ year; dead-lettered webhooks 30 days; Sentry traces 90 days. Customer-override (v2+) allows opt-in extension beyond 90 days for transcripts. Encryption: Supabase native at rest; HTTPS + HMAC-SHA256 + RS256 JWTs in transit; per-tenant runtime secrets envelope-encrypted. PII handling: OTel SpanProcessor redacts before export; lint rule prevents raw transcript text in logging contexts. Right-to-deletion: cascading delete on tenant offboarding (RLS-scoped tables make this trivial); 7-day soft-delete grace period. Compliance frameworks (SOC 2, GDPR, HIPAA) deferred until customer demand — architectural decisions already align with most controls.
